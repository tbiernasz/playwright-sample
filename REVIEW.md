# Project Review — `playwright-sample`

> **Date:** 2026-11-23  
> **Scope:** Full codebase review — config, app, tests, CI, docs, conventions, project hygiene.

---

## Executive Summary

This is a well-structured Playwright + TypeScript sample project that demonstrates an AI-assisted test-writing workflow (planner → generator → healer) on top of a zero-dependency mock shop app. The foundations are solid: good use of `storageState` for auth, proper project splitting for authenticated vs. unauthenticated flows, `fullyParallel` with per-test session minting, and comprehensive `AGENTS.md` conventions.

The improvements below range from quick wins (dead files, missing `.gitignore` entries) to medium-effort enhancements (more test coverage, server hardening, CI improvements) to architectural suggestions that would make this a stronger reference project.

**File:** [tests/seed.spec.ts](file:///c:/playwright-sample/tests/seed.spec.ts)

test.describe('Test group', () => {

## 2. Test Quality & Coverage

### 2.1 Missing test coverage

The current suite covers 4 scenarios across 3 flows. The following gaps are notable:

| Missing Scenario | Priority | Suggested File |
|---|---|---|
| **Successful login** (happy path) | High | `tests/login.spec.ts` |
| **Logout flow** (session destroyed, redirected to login) | High | `tests/logout.spec.ts` |
| **Adding the same item twice** (quantity stacking) | Medium | `tests/cart.spec.ts` |
| **Remove item from cart** (if implemented) or verify no removal exists | Medium | `tests/cart.spec.ts` |
| **Checkout with empty cart** (navigate to `/checkout` directly) | Medium | `tests/checkout.spec.ts` |
| **404 page** for unknown routes | Low | `tests/navigation.spec.ts` |
| **Unauthenticated access** to `/cart`, `/checkout`, `/` redirects to `/login` | Medium | `tests/auth-guard.spec.ts` |
| **API endpoint** `GET /api/products` returns correct JSON | Low | `tests/api.spec.ts` |

### 2.2 Login spec uses manual `browser.newContext()` — could use the `chromium-anon` project

**File:** [tests/login.spec.ts](file:///c:/playwright-sample/tests/login.spec.ts#L7-L9)

The login test manually creates a context via `browser.newContext()` and manually closes it. Since it already runs in the `chromium-anon` project (which has no `storageState`), the standard `{ page }` fixture would suffice:

```ts
test('login with a wrong password shows an error', async ({ page }) => {
  await page.goto('/login');
  // ... assertions ...
});
```

This is simpler, avoids the manual `context.close()`, and follows the convention of letting Playwright manage context lifecycle.

### 2.3 Duplicated session-minting logic in `beforeEach`

Both [cart.spec.ts](file:///c:/playwright-sample/tests/cart.spec.ts#L7-L19) and [checkout.spec.ts](file:///c:/playwright-sample/tests/checkout.spec.ts#L7-L19) contain identical `beforeEach` blocks that mint a fresh session via `request.post('/login', ...)` and inject the cookie. This is a textbook case for a custom fixture.

**Recommendation:** Create a shared fixture in a `tests/fixtures.ts` file:

```ts
// tests/fixtures.ts
import { test as base, expect } from '@playwright/test';

type FreshSessionFixtures = {
  freshPage: import('@playwright/test').Page;
};

export const test = base.extend<FreshSessionFixtures>({
  freshPage: async ({ page, request }, use) => {
    const response = await request.post('/login', {
      form: { email: 'test@example.com', password: 'password123' },
      maxRedirects: 0,
    });
    expect(response.status()).toBe(302);
    const match = /sid=([^;]+)/.exec(response.headers()['set-cookie'] || '');
    expect(match?.[1]).toBeTruthy();
    await page.context().addCookies([
      { name: 'sid', value: match![1], domain: 'localhost', path: '/' },
    ]);
    await use(page);
  },
});

export { expect };
```

Then in test files:
```ts
import { test, expect } from './fixtures';

test('first visit to the cart shows an empty state', async ({ freshPage: page }) => {
  await page.goto('/cart');
  // ...
});
```

### 2.4 `expect(match?.[1]).toBeTruthy()` violates AGENTS.md

**Files:** [cart.spec.ts:16](file:///c:/playwright-sample/tests/cart.spec.ts#L16), [checkout.spec.ts:16](file:///c:/playwright-sample/tests/checkout.spec.ts#L16)

`AGENTS.md` prohibits `expect(...).toBeTruthy()` for DOM state. While this is technically a cookie/header check (not DOM), using a more precise assertion is better practice:

```ts
expect(match).not.toBeNull();
expect(match![1]).toBeDefined();
```

Or simply throw a descriptive error:
```ts
if (!match?.[1]) throw new Error('Login did not return a session cookie');
```

## 3. Mock Server (`app/server.js`)

### 3.1 No graceful shutdown

**File:** [app/server.js](file:///c:/playwright-sample/app/server.js#L238-L240)

The server doesn't handle `SIGTERM`/`SIGINT`. When Playwright's `webServer` kills the process, it relies on hard termination. This can cause `EADDRINUSE` on fast restarts (as demonstrated during this review).

**Recommendation:**
```js
function shutdown() {
  server.close(() => process.exit(0));
  // Force exit after 3 seconds if connections hang
  setTimeout(() => process.exit(1), 3000).unref();
}

process.on('SIGTERM', shutdown);
process.on('SIGINT', shutdown);
```

### 3.2 Missing `data-testid` attributes on several elements

The cart page items and checkout page items lack `data-testid` attributes, forcing tests to rely on `getByText()` with fragile em-dash matching (`Coffee Mug — $10.00`). Per `AGENTS.md`, `getByTestId` is the highest-priority locator strategy.

**Elements missing `data-testid`:**

| Page | Element | Suggested `data-testid` |
|---|---|---|
| `/cart` | Cart item `<li>` | `cart-item` |
| `/cart` | Empty message | `cart-empty` |
| `/checkout` | Line item `<li>` | `checkout-item` |
| `/checkout` | Total | `checkout-total` |
| Confirmation | Thank-you message | `order-confirmation` |
| Dashboard | Logout link | `logout-link` |
| All pages | "Back to..." links | `back-link` |

### 3.3 No CSRF protection

The server accepts POST requests from any origin. For a mock server this is fine, but if this project is meant to demonstrate real-world testing patterns, adding a simple CSRF token would let tests demonstrate how to handle CSRF in Playwright.

### 3.4 Session IDs never expire

Sessions in `const sessions = new Set()` grow forever. For a test server this is harmless, but adding a TTL or max-size would be a more realistic model.

### 3.5 Cart items store product references, not copies

**File:** [app/server.js](file:///c:/playwright-sample/app/server.js#L204-L206)

```js
cart.push(product);
```

This pushes the actual `PRODUCTS` object reference. If a future feature mutated price (e.g. discounts), it would affect all carts. Use `{ ...product }` for safety.

## 4. Configuration

### 4.1 `playwright.config.ts` — missing `timeout` and `expect.timeout`

**File:** [playwright.config.ts](file:///c:/playwright-sample/playwright.config.ts)

The config uses all Playwright defaults for timeouts (30s test, 5s expect). For a lightweight mock app that responds in <10ms, tighter timeouts would catch hangs faster:

```ts
timeout: 15_000,
expect: { timeout: 3_000 },
```

### 4.2 Only Chromium is configured

The project only tests against `Desktop Chrome`. For a sample/reference project, adding Firefox and/or WebKit projects (even if commented out) would demonstrate cross-browser testing:

```ts
// Uncomment to run cross-browser:
// { name: 'firefox', use: { ...devices['Desktop Firefox'] }, dependencies: ['setup'] },
// { name: 'webkit', use: { ...devices['Desktop Safari'] }, dependencies: ['setup'] },
```

### 4.3 `package.json` — `"main": "index.js"` is misleading

**File:** [package.json](file:///c:/playwright-sample/package.json#L5)

There is no `index.js`. The entry point is `app/server.js`. Either update `main` or remove it (it's unused).

### 4.4 `package.json` — missing metadata

The `description`, `author`, and `keywords` fields are empty. For a sample/demo project, filling these in improves discoverability and communicates intent.

### 4.5 `tsconfig.json` — `module: "commonjs"` vs. Playwright

**File:** [tsconfig.json](file:///c:/playwright-sample/tsconfig.json)

Playwright uses its own transformer and ignores `tsconfig` module settings for test files. The `commonjs` setting is fine but could be confusing. A comment would help:

```jsonc
// Playwright uses its own TS transformer; this tsconfig is for IDE type-checking only.
```

## 5. CI Pipeline

### 5.1 Branch trigger is `master`, not `main`

**File:** [.github/workflows/playwright.yml](file:///c:/playwright-sample/.github/workflows/playwright.yml#L5)

GitHub's default branch name is `main` since 2020. If the repo uses `main`, the workflow never triggers on push.

**Recommendation:** Update to `branches: [main]` or `branches: [main, master]`.

### 5.2 No caching for `node_modules` or Playwright browsers

Each CI run does a full `npm ci` and `npx playwright install --with-deps chromium`. Adding caching significantly speeds up CI:

```yaml
- uses: actions/cache@v4
  with:
    path: |
      node_modules
      ~/.cache/ms-playwright
    key: ${{ runner.os }}-playwright-${{ hashFiles('package-lock.json') }}
```

### 5.3 Report artifact is uploaded only on failure

This is a reasonable default, but uploading on every run (with shorter retention for passing runs) enables historical trend analysis:

```yaml
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: playwright-report
    path: playwright-report/
    retention-days: ${{ job.status == 'success' && 7 || 30 }}
```

### 5.4 No matrix strategy for Node versions

Testing against a single Node version is fine for a demo, but a matrix would catch compatibility issues:

```yaml
strategy:
  matrix:
    node-version: [20, 22]
```

### 5.5 Hardcoded `--workers=4` in CI

**File:** [playwright.yml](file:///c:/playwright-sample/.github/workflows/playwright.yml#L18) and [playwright.config.ts](file:///c:/playwright-sample/playwright.config.ts#L8)

The CI workflow passes `--workers=4` on the command line, while the config also sets `workers: process.env.CI ? 4 : undefined`. This double-specification is redundant. Let the config handle it and simplify the CI command to just `npx playwright test`.

## 8. Architectural Suggestions

### 8.1 Convert mock server to TypeScript

The app server is plain JavaScript while tests are TypeScript. Converting `app/server.js` → `app/server.ts` would:
- Provide type safety for products, sessions, and request handling
- Make the whole project consistently TypeScript
- Allow sharing types between server and test helpers

### 8.2 Use a Page Object Model (POM) for larger growth

For 4 test files, inline locators are fine. If the project grows to demonstrate more complex scenarios, introducing a lightweight POM would showcase the pattern:

```ts
// tests/pages/dashboard.page.ts
export class DashboardPage {
  constructor(private page: Page) {}

  get heading() { return this.page.getByRole('heading', { name: 'Dashboard' }); }
  get cartLink() { return this.page.getByTestId('cart-link'); }

  productAddButton(name: string) {
    return this.page.getByTestId('product-item')
      .filter({ hasText: name })
      .getByTestId('add-to-cart');
  }
}
```

### 8.3 Add tags for selective test execution

The README mentions `@smoke` / `@regression` tagging but no tests use it. Adding tags would make the demo complete:

```ts
test('loads dashboard @smoke', async ({ page }) => { ... });
test('user can complete checkout @regression', async ({ page }) => { ... });
```

### 8.4 Add a `global-setup.ts` for server health check

Instead of relying solely on `webServer.url` to detect readiness, a global setup could verify the server is fully functional:

```ts
// global-setup.ts
import { request } from '@playwright/test';

export default async function globalSetup() {
  const context = await request.newContext({ baseURL: 'http://localhost:3000' });
  const response = await context.get('/api/products');
  if (!response.ok()) throw new Error('Server not ready');
  await context.dispose();
}
```
